# Lab 5 — portability verdict

The real second-provider probe used signed S3 upload/download and Lambda invocation in Sydney. Downloaded bytes matched the uploaded model data, and Lambda returned exactly the local logistic classifier's probability (difference 0.0). The probe reads the payload back from second-provider storage before invocation. The final managed-artifact cross-check is recorded separately after the GCP model is available.

Invocation was hardest: S3 URIs, signed SDK authentication, Lambda's payload/error envelope and the exact model-version field differ from the GCP HTTP service. The adapter normalizes the transport while preserving a versioned probability response. A standard-library scorer uses the exported scaler and logistic weights, so the second provider needs no expensive continuously running endpoint. The service shape is preserved even though packaging and identity are different.

The abstraction leaks at provisioning and identity. Vertex preflight demands bucket-level permissions and cannot infer that object-prefix access is sufficient. The original swap scaffold changed the provider but kept the primary bucket/project as the second endpoint configuration; the real command now requires secondary storage, region and endpoint references explicitly. These differences belong in the adapter/configuration, not in model logic.

A full migration would plausibly take 5–8 engineering days: 1–2 for identity/registry/data transfer, 1–2 for training/pipeline translation, 1–2 for serving/monitoring, and 1–2 for security/rollback/billing verification. This is a planning estimate, not measured migration time. Implementing all eleven operations for three providers would not repay its maintenance cost for this course project. Keeping model logic independent and proving the three-method seam is worthwhile; claiming complete cloud portability would conceal the remaining work.
